## 1. 结论与实施目标

**继续使用一个 Gateway 进程和同一个 HTTP/WebSocket 监听端口。** 普通 HTTP、LLM SSE 和 STT WebSocket 共享监听器，并不意味着请求串行执行。当前需要处理的是任务内部的等待关系、CPU 工作隔离和数据库事务一致性，不是拆端口。

推荐实施顺序：

1. 固化四个问题的回归检查，保留可重复的修改前证据。
2. 修正 MySQL 错误分类，恢复已有的有限事务重试。
3. 修复租约回收与续租竞态，统一相关事务的加锁顺序。
4. 修复 STT 双向队列互等，补齐连接、停止和资源清理的时间边界。
5. 将密码哈希与校验移出异步工作线程，并限制 CPU 并发。
6. 完成隔离数据库、模拟上游、真实协议链路及混合负载验收，再安排部署。

本期成功标准：

- 队列满时，会话仍能处理生命周期信号；正常下游恢复消费后，双向流可以继续推进。
- 续租先完成的有效预占不会被过期回收；回收先完成的终态不会被续租或激活复活。
- MySQL `1213`、`1205` 能触发既有重试，其他错误不会被误判；重试不产生重复预占或扣费。
- 密码计算不再占用 Tokio 异步工作线程；请求取消不能绕过 CPU 并发上限。
- 正常音频顺序、转写边界、事件序号、预占与结算语义保持兼容。

## 3. 范围与不变量

### 3.1 必须保留

- HTTP、SSE、WebSocket 的现有地址、鉴权、ticket 使用方式及协议版本。
- `PCM S16LE / 16 kHz / 单声道`、音源隔离、音频 FIFO 和现有帧限制。
- `stt.ready`、`transcript`、`quota.warning`、`session.ending`、`session.ended` 的字段结构，以及单会话单调递增的 `seq`。
- 额度不为负、幂等键不变、同一会话的 `final` 使用事件最多一条。
- Argon2id 参数、随机盐、现有密码长度校验、CSRF、登录限流、账户锁定、MFA 和错误信息保护。
- Gemini 的会话续接、旧连接尾部排空、转写顺序与 utterance 边界处理。

### 3.2 本期不做

- 拆 HTTP/WS 端口、拆微服务、增加实例、增加 Redis 或消息队列。
- 改变价格、额度桶优先级、订阅支付、用户套餐或真实用户余额。
- 全面重写所有 Provider 为统一 Actor 框架，或增加通用任务调度平台。
- 放大队列掩盖堵塞，静默丢弃音频或 final 转写后继续报告正常完成。
- 修改桌面界面或当前工作区中其他人的隐形助手改动。
- 顺带重构完整 LLM 生命周期、日志系统或数据库连接池。共享事务函数的调用点必须适配，但不扩大到无关行为。
- 承诺数据库长期不可用或进程强杀时精确恢复所有计量。本期不新增持久化计量日志或补偿队列，该恢复能力仍是独立议题。

## 4. 关键设计决策

| 决策 | 采用方案 | 不采用方案与理由 |
|---|---|---|
| STT 双向推进 | 保留会话协调循环，将等待中的音频、续租和客户端写入作为持久 future 同时轮询 | 只加超时不能消除队列互等；全面拆成多层转发任务会扩大改动与状态同步面 |
| 慢端处理 | 短时背压等待；超过明确预算后结束会话并清理 | 无限缓存会把网络故障转换成内存问题 |
| Adapter 生命周期 | 保留现有协议状态机，增加受会话拥有的取消信号和任务回收 | 不能仅把 `Close` 排在已满的音频命令队列末尾 |
| 过期回收 | 候选扫描不作为决策；持行锁后再次判断状态与到期时间 | 不引入全局分布式锁或长事务批量锁住所有过期预占 |
| MySQL 重试 | 使用数字错误号，保留现有最多 3 次尝试 | 不匹配错误文本，不将全部 `HY000` 当成可重试错误 |
| 密码工作 | `spawn_blocking` 前申请进程内 CPU permit，满额快速返回可重试限流 | 不使用无限排队的 `spawn_blocking`，不降低 Argon2 成本 |

Tokio 的 `select!` 在分支完成后执行该分支的 handler；handler 内的长等待不会同时继续轮询原来的其他分支。持久 future 必须保留在循环外，通过引用重复轮询，而不是每轮重建发送或数据库操作。[Tokio 1.53.1 select 文档](https://docs.rs/tokio/1.53.1/tokio/macro.select.html)

## 5. GW-03：恢复正确的 MySQL 有限重试

### 5.1 修改设计

涉及：[entitlement.rs](../server/src/entitlement.rs) 的 `retryable_mysql`、`reserve`、`top_up`、`settle`。

1. 从 `sqlx::Error` 取得数据库错误，使用安全的类型检查/downcast 取得 `sqlx::mysql::MySqlDatabaseError`。
2. 仅对 `number()` 为 `1213` 或 `1205` 返回 `true`；非数据库错误、非 MySQL 错误、其他号码返回 `false`，不使用会 panic 的强制 downcast。
3. 保留现有最多 3 次尝试，以及两次重试前的 20 ms、40 ms 等待。
4. 每次失败结束当前事务，再以新的事务重试完整操作；禁止只重放某条 SQL，也不能持有行锁睡眠。
5. 幂等键、请求哈希、最终事件键在重试间保持不变。连接中断或提交结果不明不自动归为锁错误。
6. 在实际重试和耗尽重试处增加结构化日志：`operation`、`attempt`、`mysql_number`、`sqlstate`、耗时。不要记录 SQL 绑定参数、口令或连接串。

SQLx 的 `code()` 表示 SQLSTATE，`number()` 才是 MySQL 的细分数字错误号，这是本次分类修复的依据。[SQLx 0.8.6 MySqlDatabaseError](https://docs.rs/sqlx/0.8.6/sqlx/mysql/struct.MySqlDatabaseError.html)

本阶段不为所有数据库函数增加重试框架。`release` 的失败由调用方记录，reaper 在后续周期重新处理；续租数据库错误进入会话错误处理。若后续确定这两个入口也需要重试，再沿相同事务边界添加，不借本次修复扩大范围。

### 5.2 回归要求

- 分类检查覆盖 `1213 / 40001`、`1205 / HY000` 和至少一个不应重试的错误，例如 `1062`。
- SQLx 错误对象使用真实 MySQL 返回值；`SIGNAL` 注入使用 `sqlx::raw_sql`，不使用服务器不支持的预处理 `SIGNAL`。
- 分类检查放在能访问私有函数的模块测试中，数据库依赖测试按现有方式 `#[ignore]`；不为测试把分类函数改为公开 API。
- 至少一个真实锁冲突用例通过现有 `reserve/top_up/settle` 入口执行，验证重试后只出现一次业务效果；仅注入错误不能证明事务回滚正确。
- 持续冲突时最多尝试 3 次；余额、allocation 和 `usage_events` 数量可核对。
- 重跑基线的追加预占与 LLM 超预占结算用例，防止 `Option<u16>` 修复退化。

**时间边界：** 20/40 ms 只是退避，不包含单次 SQL 的锁等待。不得据此宣称数据库操作在 60 ms 内结束；STT 的总操作预算在第 7 节单独约束。

## 6. GW-02：租约回收与续租原子化

### 6.1 持锁后的回收判断

涉及：[entitlement.rs](../server/src/entitlement.rs) 的 `release`、`reap_expired`。

保留当前按到期时间扫描最多 100 条候选的结构。候选只表示“需要检查”，不表示“可以退款”。

单条回收按以下顺序执行：

1. 获取不可变的账户关联，开启事务，调用现有 `lock_account`。
2. 对目标 reservation 执行 `SELECT ... FOR UPDATE`，读取 `session_id`、`state`、`expires_at`。
3. 若已是终态，提交空操作并返回“未释放”。
4. 对 `expired=true` 的请求，在已取得锁后获取数据库当前时间，并检查 `expires_at <= 当前时间`。已续租则提交空操作并返回“未释放”。不要复用扫描时刻或等待锁之前的应用时间。
5. 只有判断成立才执行现有 allocation 返还、reservation 终态和 session 终态更新。
6. 提交成功后才返回“实际释放”。

最小接口调整：保留现有对外 `release(...) -> Result<(), AppError>` 供 STT/LLM 失败路径使用；把内部释放事务提取为返回 `Result<bool, AppError>` 的私有函数。reaper 调用内部函数，仅在 `true` 时计数；手动释放继续使用 `expired=false`，不受过期条件限制。

reaper 对每个候选失败记录结构化错误并继续其他候选，下一周期重试；不能继续把所有 `Ok(())` 都计为已退款，也不能用 `.is_ok()` 静默吞掉数据库错误。

### 6.2 续租锁序与返回值

当前 `touch_lease` 先更新 `ai_sessions`，再更新 reservation；结算和回收则先锁 reservation、最后更新 session。调整续租，使同账户的相关事务沿既有账户行锁串行化。

锁序规则：

```text
accounts 行锁
  -> 已存在的 quota_reservations 行锁
  -> 必要的现有 allocation / bucket 操作
  -> ai_sessions 状态或租约更新
  -> COMMIT
```

这不是要求重排所有插入或桶操作。新建 reservation 的插入顺序保持现状；本期修正的是续租/激活对已有 reservation 的访问顺序。若同一会话读取多个 reservation，按固定 ID 顺序加锁，不依赖当前“通常只有一个”的假设。

`touch_lease` 的具体行为：

1. 先锁账户，再锁该会话的 reservation，最后检查/更新 session。
2. 仅允许有效账户、`ACTIVE` reservation 和允许续租的 session 状态继续。
3. 持锁后计算同一个新到期时间，在同一事务中写入两张表。当前已过期但尚未回收的活动会话可以续租，以谁先获得锁为准。
4. 改为 `Result<bool, AppError>`：`true` 表示续租成功；终态或不允许续租返回 `false`，数据库失败仍返回错误。
5. STT 调用方遇到 `false` 停止继续接纳音频，不再把“更新了 0 行”当作续租成功。

### 6.3 激活与终态的一致性

同一不变量还要求检查 `mark_active`：当前更新没有终态条件，不能在 reaper 已完成后把 `ABANDONED` 改回 `ACTIVE`。

- 在同一账户/预占锁序下确认 reservation 仍是 `ACTIVE` 且按数据库当前时间尚未过期，session 处于允许激活的前置状态，才写入激活信息。初次连接完成不能作为复活过期预占的理由。
- 不改变方法的成功返回形态；不允许激活时返回现有合适错误。
- STT 保留激活失败后的释放和清理路径。
- [llm.rs](../server/src/llm.rs) 当前忽略 `mark_active` 的结果，必须改为处理失败、结束该上游流并清理 cancellation/计数；只适配这个共享调用点，不重写整个 LLM 流程。

这两项是本次锁序与状态约束的配套修复，不把未单独复现的激活竞态冒充第五个已复现问题。

### 6.4 并发交错验收

| 交错 | 期望结果 |
|---|---|
| reaper 已选出过期候选，续租先取得锁并提交，随后回收取得锁 | reservation/session 仍有效，余额不返还，实际回收数为 0 |
| reaper 先取得锁并提交，随后续租 | 续租返回 `false`，终态不复活，额度只返还一次 |
| 同一 reservation 同时结算和回收 | 只有一个终态操作生效，不重复返还、不重复扣费 |
| 重复回收、重复手动释放 | 后续操作为无副作用空操作，计数不增加 |
| 未到期的连接失败，调用 `release(..., false)` | 仍可立即返还预占，不被新增到期条件阻止 |
| 回收完成后激活，分别从 STT 和 LLM 路径进入 | 激活失败，上游停止，不继续提供未受有效预占保护的工作 |

复现采用独立 MySQL schema 和明确的 barrier/锁等待检查，不依赖“睡眠若干毫秒后猜测事务已走到某行”。续租新增账户锁后，不能照搬“持有账户锁再同步等待续租”的旧探针，否则测试自身会死锁；应先固定候选 ID，完成续租，再调用真实的持锁回收逻辑，并另测真实并发争锁。

## 7. GW-01：STT 双向推进与生命周期约束

### 7.1 解除队列相互等待

涉及：[sessions.rs](../server/src/sessions.rs) 的 `proxy_stt`，以及 [providers/stt.rs](../server/src/providers/stt.rs) 的发送契约。

保留一个会话协调器，不增加逐帧 `spawn`，不增加无界转发缓冲。将可能等待的工作变为循环外持有、循环内轮询的操作：

| 待完成操作 | 最大在途数量 | 等待期间仍要推进 |
|---|---:|---|
| 音频校验后的补预占及 `send_pcm` | 1 帧 | Provider 结果、客户端输出、续租、shutdown、总时限 |
| 客户端 WebSocket 写入 | 1 条 | 音频发送、续租、shutdown、总时限 |
| 账户检查及续租 | 1 次 | 两个数据方向、shutdown、总时限 |

协调循环的 handler 只更新状态、完成计数或安装下一项待完成操作，不在 handler 中串行等待上述 I/O。其他分支就绪时保留原 future，不能重建补预占请求或丢弃发送中的音频。

具体约束：

- `send_pcm` 等待队列容量时，只要客户端可写，就继续从 `provider_rx` 取出并发送转写，解除已复现的循环依赖。
- 客户端写入由一个所有者串行执行，统一管理 `seq`；不能让 Pong、转写和结尾通知同时争用同一个 sink。
- 客户端暂时不可写时，保留当前待写消息，暂停进一步取出 Provider 结果，以已有 32 槽事件队列承接背压。超过预算后终止，不创建新的无限结果列表。
- 一帧音频未完成接纳前暂停读取后续客户端数据，不另建音频积压队列；已有命令队列仍为 16，最多额外持有 1 帧。
- `quota.warning` 和 `session.ending` 按现有顺序输出，只保留该固定控制序列，不在故障期间持续生成通知。
- deadline/shutdown 分支不会被持续就绪的数据饿死；如使用 `biased`，控制分支置前，剩余分支仍须测试公平推进。

**停止语义边界：** `stt.stop` 与音频共用一条有序 WebSocket。暂停读取时，尚未读到的 stop 不可能越过之前的 TCP 数据立即生效。本期不新增控制连接：正常可读时立即处理 stop；音频接纳持续卡住时由下述总预算强制结束。不能对网络中尚未被读取的 stop 承诺 10 ms 响应。

### 7.2 计量与取消安全

当前 `received_samples`、`forwarded_samples` 都在 `send_pcm` 成功后增加。这里成功只表示进入 Adapter 队列，不代表厂商已接收或确认计费。

- 本期保持“Gateway 接纳进入 Adapter 队列”这一既有扣费边界，不悄悄改成 socket 读取时计费，也不改成厂商 ACK 计费。
- 成功入队与样本计数之间不能再插入 `.await`；协调器必须在同一次完成处理中恰好增加一次计数。
- 尚未成功入队的音频因超时或取消而结束，不增加已接纳样本数，不在重连时自动重放。
- `send` 的 pending future 在普通分支切换时必须被保留；只有决定结束会话时才能取消。若改用预留容量接口，必须先取得 permit，再完成不可分割的入队/记账步骤。
- 补预占可能在取消边界已经提交；最终结算应在新的事务中重新读取实际 held 值，而不是用内存中的旧数值做退款。
- `Finish` 必须排在已接纳音频之后；只有一个最终结算入口，继续使用 `event_key="final"`。
- 异常中断继续标记 `ESTIMATED`。现有 `forwarded_audio_ms`/`provider_audio_ms` 不是新增的厂商送达证明，不以本次改动声称取得了这种证明。

Tokio 明确指出，取消队列 `send` 会丢弃尚未发送的消息，且 `Ok` 不保证接收方最终消费；需要保留消息时可使用容量预留接口。[Tokio mpsc Sender 文档](https://docs.rs/tokio/latest/tokio/sync/mpsc/struct.Sender.html)

### 7.3 时间预算

以下是实施初值，不是本轮测得的生产 SLA。作为少量内部常量使用，不新增一组环境变量；测试允许注入更短预算。部署时校验这些预算与实际 reservation TTL 的关系。

| 阶段 | 初始预算 | 超时行为 |
|---|---:|---|
| 初次上游连接及协议初始化 | 整体 30 秒 | 取消连接工作，释放未使用预占；保留 Gemini 现有更短的内部握手限制 |
| 单帧接纳：必要补预占加命令入队 | 整体 5 秒 | 停止接纳，按已成功接纳量结算 |
| 单次客户端写入 | 5 秒 | 标记慢客户端，关闭该连接，继续完成数据库收尾 |
| 单次上游写入或结果投递等待 | 5 秒 | 结束 Adapter，向会话传递错误或任务结束，不无限等待错误队列 |
| 一轮账户检查及续租 | 整体 5 秒 | 结束会话，不在租约可能丢失后继续发送新音频 |
| 正常 `Finish` 与尾部结果排空 | 整体 2 秒 | 保留现有上限，超时转强制清理 |
| Adapter close、取消与回收 | 整体 1 秒 | 中止未结束的异步任务并回收句柄 |
| 最终结算 | 整体 5 秒，含现有有限重试 | 记录结算失败/结果不明，不把它当作成功退款 |
| `session.ended` 与客户端 close | 合计 1 秒 | 无法发送则放弃连接，不阻塞资源释放 |

会话总时限和 shutdown 从连接阶段开始受监管，不能等 `connect().await` 返回后才生效。初次连接未完成时，不接纳音频，也不启动无限握手重试。

进入结束状态后停止创建新的音频/续租工作；收尾采用独立预算，不能因为 shutdown token 已触发而连最终结算也直接跳过。上述顺序清理的预算上限约为 9 秒，加调度与数据库取消回收开销；这是 STT 清理目标，不是整个 HTTP 服务器的无条件退出时限。

数据库 future 超时不等于服务器端操作已经确定回滚。必须验证 SQLx 取消后的连接归还/事务回滚行为；结算结果不明时保留会话 ID、reservation ID 和计量日志用于核对，禁止无条件再调用 `release` 退款。数据库长期故障后的准确计量恢复不由当前 reaper 自动保证。

### 7.4 Adapter 任务归属与清理

涉及 `[SttConnection, ChannelSink]` 及三个 Adapter：

- [deepgram.rs](../server/src/providers/deepgram.rs)
- [gemini_live.rs](../server/src/providers/gemini_live.rs)
- [volcengine.rs](../server/src/providers/volcengine.rs)

实施要点：

1. `SttConnection` 持有 Provider 工作任务的生命周期句柄/guard 和独立取消信号；会话取出 sink/events 后，该所有权仍必须活到收尾结束。
2. 取消等待放在覆盖整个 Adapter 工作 future 的外层，使内部选中分支正在等待 socket 或事件队列时仍可终止。
3. 上游连接、setup 写入、音频写入、keepalive/Pong、结果投递和错误投递均有适当时间边界。错误通道已满时不能为发送错误再永久等待。
4. 正常 stop 先 Finish 与 drain，再 close；异常/超时通过带外取消终止任务，不依赖排入 `Close` 成功。
5. 超过清理预算时 abort 异步任务并等待其完成；Drop guard 仅作兜底，正常路径仍要显式观察任务结果。
6. Gemini 的 `pending_open` 是子任务，所有退出路径都必须中止并回收它。仅丢弃 `JoinHandle` 不代表取消；旧连接和替换连接也必须随所属会话释放。
7. 被取消或超时的 WebSocket 写入不重新发送同一帧；若不能确认 sink 可继续安全使用，就丢弃连接，跳过最后通知，但不跳过结算。

保留 `finish_while_draining` 的并发排空思路及其现有测试。这里不是要求三家 Provider 的协议状态机统一重写。

### 7.5 退出原因与兼容性

优先保留 `user_stop`、`session_limit`、`gateway_shutdown`、`quota_exhausted`、`gateway_error` 等既有终止原因。新增细分等待阶段放在结构化日志的 `phase` 字段，不要求桌面端识别新协议版本。

至少记录 `session_id`、`provider`、`phase`、`elapsed_ms`、`accepted_audio_ms`、`usage_status`、`settle_outcome`。不要记录原始音频、转写、ticket、密钥或带凭证的上游 URL。

## 8. GW-04：密码工作线程隔离与并发限制

### 8.1 复用 AuthService

涉及：[auth.rs](../server/src/auth.rs) 和 [oidc.rs](../server/src/oidc.rs)。

在现有 `AuthService` 中增加一个共享的 `Arc<Semaphore>`，以及异步 hash/verify 入口。继续复用现有同步密码函数，不增加独立认证服务、Rayon 或线程池库。

初始并发数采用：

```text
C = max(1, min(2, 可用逻辑 CPU 数 - 1))
获取 CPU 数失败时使用 1。
```

这是单实例阶段的保守初值，不是已测最优值。以现有每次 Argon2 约 19 MiB 的参数计算，C=2 的算法内存量级约为 38 MiB，不含进程其他内存。上线前按容器实际 CPU/内存配额验证，不凭宿主机核数提高并发；暂不增加环境变量。

工作流程：

1. 保留已有请求大小、CSRF、限流、密码格式及业务前置检查。
2. 在异步上下文用 `try_acquire_owned` 获取 CPU permit；容量已满立即返回可重试的 `429 / RATE_LIMITED`，不积压大量带密码的等待任务。
3. 将 permit 和必要的 owned 字符串一起移入 `spawn_blocking` 闭包。
4. 闭包内执行同步 hash/verify，结束时释放 permit；不在数据库事务或锁内计算密码。
5. 正常等待 JoinHandle，panic/JoinError 按内部错误处理；不能映射成“密码错误”并增加失败次数。
6. 请求取消后，即使外部等待 future 被丢弃，正在执行的闭包仍持有 permit，直到计算真正完成。

Tokio 的阻塞线程池默认上限较大，CPU 工作需要自行限并发；已经开始的 `spawn_blocking` 不能靠 abort 停止。这是 permit 必须放在闭包内的原因。[Tokio 1.53.1 spawn_blocking 文档](https://docs.rs/tokio/1.53.1/tokio/task/fn.spawn_blocking.html)

### 8.2 必须覆盖全部入口

| 当前调用点 | 修改方式 | 不能退化的行为 |
|---|---|---|
| `oidc::login` 已存在用户 | 调用异步 verify | 正确/错误密码、锁定状态、失败计数、MFA 分支 |
| `dummy_password_check` 未知用户 | 使用同一 CPU 限制，在阻塞闭包内初始化/使用 dummy hash 并校验 | 不能遗漏首次 `OnceLock` 初始化中的同步 Argon2；不额外暴露账户存在性 |
| `complete_password_action` | 调用异步 hash，继续在数据库事务前完成计算 | 邀请激活、密码重置、确认密码、action token 幂等消耗 |
| `disable_totp` | 调用异步 verify | 原密码和第二因素都有效才禁用 MFA |
| 同步函数的测试调用 | 可继续用于明确的非在线测试夹具 | 不以测试工具调用代替在线入口覆盖 |

未知账户与正常密码校验路径使用相同的过载策略。保留已有锁定/停用账户分支，不把本次工作扩展成完整的登录时序防枚举重构，也不宣称网络响应绝对等时。

OIDC 入口须区分三种结果：凭证无效、CPU 容量不足、内部执行失败。后两者不能增加密码失败计数，密码设置/重置在容量不足时不能消费 action token。

### 8.3 验收方式

- 并发执行数量始终不超过 C；C 个工作被测试 gate 挂起时，第 C+1 个请求可立即得到限流结果。
- 取消所有外部等待者后，permit 仍被占用，直到已启动闭包真正退出。
- 2 个 Tokio 工作线程环境下，密码任务执行期间定时器与轻量 HTTP 能继续推进。
- 调度正确性用可控 gate/barrier 证明，避免把“必须小于 10 ms”写成受机器噪声影响的 CI 断言。
- 另用 release 构建测量真实 Argon2 并发下的健康接口延迟与 CPU；debug 约 287 ms 的历史结果不作为生产阈值。
- 正确密码、错误密码、未知用户首次请求、未知用户重复请求、非法新密码和过载响应全部覆盖。

### 11.2 隔离与安全要求

- `TEST_DATABASE_URL` 只指向独立测试 schema。测试会迁移并写表，不能指向当前业务库。
- 使用唯一 schema/账户/幂等键；测试结束只清理本轮创建的对象，不 truncate 共享表。
- 需要锁等待观测权限的用例与普通测试账号分开说明；不能因权限不足静默跳过后报告通过。
- 假上游和测试 Gateway 使用 `127.0.0.1:0` 动态端口，不占用或关闭当前用户的 8787 服务。
- 假上游使用测试凭证且不访问公网模型；真实厂商测试另行准备测试账户、额度与授权。
- 测试密钥使用临时目录；日志和报告不输出密码、token、数据库连接串或真实内容。

## 12. 性能验收与可观测性

### 12.1 最小观测面

复用现有 tracing 和 `/metrics` 的 STT/LLM active/started 数据，不先引入新的监控依赖。

| 观测项 | 获取方式 | 关注点 |
|---|---|---|
| HTTP 与 WS 应用层延迟 | 负载客户端记录 p50/p95/p99 | HTTP 首屏响应与持续转写是否互相拖慢 |
| 各阶段等待、结束原因 | 结构化日志中的 phase/elapsed/outcome | 区分慢客户端、慢上游、数据库等待和主动停止 |
| 实际重试与耗尽次数 | MySQL 分类日志 | 1205/1213 是否被识别，重试是否放大压力 |
| 候选跳过与实际回收 | reaper 结构化计数/日志 | 续租候选跳过不是错误；误退款必须为 0 |
| 密码在途与拒绝 | 测试观测、容量拒绝日志 | 是否始终遵守 C，是否出现取消后超发 |
| CPU、RSS、线程、FD、连接数 | 测试进程和数据库观测 | 是否有持续增长或无法回落 |
| 额度和终态 | 测试数据库核对 | 非负、无重复扣费、无已续租误回收 |

仅记录慢操作、重试、拒绝和结束摘要，不为每个音频帧新增 info 日志。会话 ID 可用于结构化日志关联，但不作为高基数 metrics 标签。

### 12.2 混合负载步骤

1. 使用 release 构建、固定 CPU/内存限制和独立数据库，记录无密码突发时的基线。
2. 以 20 ms PCM 帧、每秒 50 帧模拟实时音频，避免一次性灌入大量音频造成与真实使用不符的结果。
3. 依次测试 10、25、50、80 条 STT 连接，每档持续至少 5 分钟；加入最多 10 条 LLM 流和固定频率健康/就绪请求。
4. 加入密码并发 C、C+4 的突发；保留原登录限流，用受控测试身份/IP 记录正常限流与 CPU 过载，不能临时关闭安全限制换取高吞吐。
5. 单独测试混合 AI 活动数达到 100 后的新请求拒绝与预占返还，不把准入拒绝统计为死锁或实现失败。
6. 对已稳定通过的最高档持续至少 20 分钟，跨过多个 120 秒租约和多次 top_up；注入慢客户端、上游停读、数据库锁等待和会话取消。
7. 停止负载后等待清理预算，检查 active、permit、任务、FD 和数据库连接回到合理空闲水平。RSS 可能因分配器保留不立即回到起点，应检查重复循环是否持续增长，而非要求字节级回零。

容量探测逐级推进，不保证最高档一定通过。先达到 CPU/内存/数据库瓶颈就停止增加负载，并将最后通过档记为“该测试环境下的验证容量”；不得把本机结果直接写成生产容量。

### 12.3 验收门槛

- 硬门槛：误回收、重复扣费、负余额、无限等待、遗漏在线同步密码入口、超出 C 的密码并发均为 0。
- 硬门槛：受控满队列测试中，deadline/shutdown 不依赖另一端主动解堵；恢复消费的正常链路没有新增丢帧或乱序。
- 硬门槛：故障结束后，Provider 与 Gemini 子任务在配置的清理预算及测试容差内退出；不能只看到主会话计数下降。
- 延迟目标初值：在健康的本地 release 混合负载档位，轻量 HTTP 的 p99 不超过 250 ms；密码突发时不出现与每次密码计算等长的工作线程停顿。这是待实测的验收起点，不是已达成的 SLA。
- 正常 stop 在实际读取到控制消息后及时进入收尾；有音频背压时，等待上限按第 7.3 节计算，不能把尚未读取的 stop 当作已处理。
- 测试期间真实厂商响应耗时与 Gateway 自身增加的排队耗时分开记录；模型速度不作为 Gateway 调度性能的替代指标。

### 13.1 上线前

1. 汇总每个问题的修改前失败、修改后通过证据，附提交号、构建模式、测试环境与未覆盖项。
2. 确认没有 migration、协议版本、价格版本或密钥变化；确认工作区中其他改动没有被混入修复构建。
3. 使用独立预发布 Gateway 完成真实 HTTP、WS Upgrade 和各已启用厂商的短会话检查；真实厂商调用须有测试预算和授权。
4. 核对生产 CPU/内存配额、实际租约 TTL、入口代理的 WS/SSE 超时和现有启动方式。
5. 保留旧的已验证二进制/镜像与配置版本；备份数据库和既有 OIDC 密钥，备份不得写进仓库。

### 13.2 发布方式

当前 ticket、限流和 cancellation 是进程内状态，不采用两个生产实例随机分流的百分比灰度。先在隔离环境验证，再在明确维护窗口替换单实例。

- 先通知正在使用的人并安排会话结束，确认运行进程的 cwd、启动来源和监听器后再操作。
- 通过既有运行管理方式发送 `SIGTERM`，观察旧实例退出；不要仅凭端口号杀进程，也不强行占用已有端口。
- 启动新构建后验证 `/healthz`、`/readyz`、一次登录、一次 STT 创建/Upgrade/stop，以及一条 LLM 请求。
- 至少观察多个租约周期，核对异常终止、数据库重试、误回收、CPU 过载和最终结算结果。

当前 `main.rs` 的 15 秒 tracker 等待发生在 `axum::serve` 返回之后，不能据此宣称整个进程一定在 SIGTERM 后 15 秒退出。本期 runbook 必须写清 STT 清理预算与进程级关停边界；完整 HTTP/LLM 的强制退出预算是另一项独立变更。

### 13.3 回退触发与步骤

立即停止放量或回退的条件：

- 发现有效续租被回收、重复扣费、额度负数或 session/reservation 终态冲突。
- 正常负载出现可复现的音频/转写丢失或乱序，尤其是 Gemini 轮换尾部丢失。
- Provider 任务/连接持续泄漏，或正常登录大量错误而不只是预期的可重试限流。

回退只替换本轮代码构建，不回滚或清空数据库，不改写 usage 行掩盖异常。涉及额度的异常保留 session/reservation/usage 证据，通过既有审计调整流程处理。旧构建仍含已知问题，回退不是长期修复；必要时经授权临时关闭受影响的 hosted 工作负载。

由于本期不变更数据库结构，代码回退不需要逆向 migration。拆分提交允许保留已验证的 MySQL 分类与租约修复，只撤回发生回归的 STT 或密码部分；STT 生命周期相关文件必须作为同一契约整体回退。
